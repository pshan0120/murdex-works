# 앙코르 기획안

메모리얼 미스터리 (머더프리) / 1인용 스토리플레잉
초안 작성일: 2026-08-24

## 1. 한 줄 컨셉

거꾸로 흐르는 시간 속에서, 노견이 된 강아지와의 마지막 5분들을 하나씩 되짚어 올라가다가 처음 가족이 된 날에 도착하는 1인용 추모 스토리플레잉.

## 2. 제목

**앙코르**

- 실제 작품 제목은 "앙코르"다. 원어 표기 "Encore"는 아래에서 제목의 뜻을 설명하기 위해 병기하는 것일 뿐, 등록 제목에 포함되지 않는다.
- 표면적 의미: 공연 마지막 곡 이후 관객이 앙코르를 청하듯, 이 작품도 "한 곡 더"를 청하는 구조다.
- 실제 의미: 프랑스어 원어(Encore)의 "아직", "다시"라는 뜻. 이별 후 가장 많이 되뇌었던 "아직 보낼 준비가 안 됐는데"와 "다시 한 번 보고 싶다"를 함축한다.
- 제목만 보면 밝게 읽히지만 실제로는 그리움을 담고 있다는 이중성이 작품 전체의 톤(밝은 표면 + 상실의 이면)과 정확히 같은 결을 가지고 있다. 제목과 구조가 같은 원리로 설계된 셈이라 이 제목은 그대로 가도 좋다고 본다.

## 3. 장르 정의: 머더프리 / 메모리얼 미스터리

사람이 죽지 않으므로 머더 미스터리는 성립하지 않는다. "메모리얼 미스터리"라는 신설 카테고리로 제안한다.

- 추리 요소는 사실상 없고, 정체를 밝히는 대신 **의미를 뒤늦게 깨닫는 구조**로 미스터리성을 대체한다. (아래 4장)
- 참고: [머더미스터리 평가기준](works/미스터리_평가기준.md)의 11항목 중 "반전의 개연성과 참신성", "텐션 곡선", "엔딩의 무게"는 그대로 적용 가능하지만 "동기의 설득력", "페어플레이(범인 특정)" 항목은 이 장르에 맞게 재해석이 필요하다. (10장 참고)

## 4. 핵심 기믹: 역행하는 시간

- 실제 시간 순서: 입양일(나이 0) → ... → 마지막 날(나이 16) → 이별 후 지금.
- 플레이 순서: 이걸 뒤집어서, 이별에 가장 가까운 시점부터 시작해 입양일로 거슬러 올라간다.
- 플레이어는 이 사실을 모른 채 진행하다가, 마지막 조사 단계 즈음(=실제로는 입양 첫해) "시간이 거꾸로 흐르고 있었다"는 것을 스스로 깨닫는다.
- 이 반전은 정보 공개가 아니라 **감정의 방향 전환**으로 기능한다. "죽음에서 시작해 삶으로 끝난다"는 구조 자체가 이 작품의 주제고, 미스터리 틀은 그 주제를 체험시키기 위한 장치다. 잘 짜인 설계라고 생각한다.

### 구조적 반전 장치: 표시 1단계 진입 시 첫 단서("데려오기" + 둘째 강아지 "똘이")

표시 1단계에 처음 들어가면 단서가 전부 보이는 게 아니라 "{dog_name_2}"(둘째 강아지, 이미 공개된 단서)와 "{dog_name} 데려오기"(조사 가능한 단서) 두 개만 있고, "데려오기"를 조사해야 나머지 단서(예: 산책하기, 계단 오르기)가 게임보드에 공개된다.

- **실제 사연**: 사용자의 집에는 원래 강아지가 두 마리 있었다 — 아리(엄마)와 똘이(아들). 아리가 떠난 지금, 똘이만 남아 있다. 이 사연을 살려 표시 1단계에 똘이를 등장시킨다.
- 단서명("데려오기")과 내용은 강아지를 새로 데려온 날처럼 읽히게 쓴다. 사용자가 직접 쓴 원안:
  > 나는 우리 집에 한 마리의 강아지가 더 생기길 바랐다. 그리고 그 소원이 이루어졌다. 지금 우리 집에 개가 두 마리 있다. 나는 {dog_name}를(을) 품에 안고 있다. 나는 {dog_name}에게 인사했다. "안녕." 그러니까 {dog_name}도 나를 쳐다본다. {dog_name_2}는(은) 그 모습을 불안한 눈빛으로 쳐다보고 있다.
  
  플레이어는 이걸 "둘째 강아지를 분양받아 온 날, 기존에 있던 첫째가 낯선 냄새에 불안해하는" 훈훈한 장면으로 읽는다.
- **실제로는 정반대다.** "안녕"은 인사가 아니라 **작별 인사**이고, "{dog_name}도 나를 쳐다본다"는 표현은 새 강아지의 호기심이 아니라 **아리의 마지막 움직임**이다. {dog_name_2}(똘이)가 불안한 눈빛인 것도 새 식구를 향한 경계가 아니라 **엄마 개의 죽음을 직감한 반응**이다. 문장 자체는 사실만 관찰해서 남기고(7장 규칙 그대로) 어느 쪽으로도 해석 가능하게 열어뒀을 뿐이다.
- 이 단서는 게임 전체에서 시간상 가장 나중에 벌어진 사건(사망 이후, 유골을 안고 돌아온 순간)이면서 플레이어가 가장 먼저 만나는 단서이기도 하다 — 4장 전체의 "역행하는 시간" 구조를 표시 1단계 안에서 한 번 더 축소판으로 반복하는 장치다.
- 표시 16단계("입양 첫해")의 첫 단서("{dog_name}를(을) 안고 처음 이 집에 들어섰다")와 문장을 의도적으로 비슷하게 맞춘다. 게임을 시작할 때(가짜 입양처럼 읽히는 순간)와 반전이 완전히 풀리는 마지막 순간(진짜 입양)에 같은 이미지를 두 번 겪게 되는 문장 echo다.
- **개인화 변수 확장**: 8장의 `{dog_name}` 패턴이 그대로 `{dog_name_2}`(둘째 강아지 이름, 기본값 "똘이")로 확장된다. 별도 설계가 필요 없다 — `Question.variable_key`를 하나 더(예: "dog_name_2") 만들고 질문("함께 지내고 있는 다른 강아지가 있다면 이름을 알려주세요")을 하나 더 배치하면 끝난다.
- **{dog_name_2}의 등장 범위와 퇴장 규칙**: 똘이는 실제로 {dog_name}이 6살일 때(10월) 태어났다. 5장 공식(내부 나이 = 17 − 표시 단계)으로 계산하면 내부 6살 = 표시 11단계다. 즉 **표시 12단계(내부 5살)부터는 똘이가 절대 등장하면 안 된다.** 표시 11단계는 경계 지점(그 해 안에서 10월 전후로 존재 여부가 갈림)이라 등장 여부를 신중히 고른다.
  - **주의: 똘이의 탄생을 명시적인 장면으로 연출하지 않는다.** "막 태어난 강아지"처럼 나이를 알아볼 수 있게 묘사하면, 지금까지 지켜온 "설명하지 않고 관찰만 남긴다"는 서술 원칙(7장)이 깨진다. 반전의 초점은 어디까지나 {dog_name}(아리)이지 {dog_name_2}(똘이)가 아니다.
  - 표시 1~11단계에서 똘이는 **{dog_name} 중심의 단서 안에 가끔(매 단계가 아니라 이따금, 단계당 많아야 1~2개 단서 정도) 배경처럼 등장**한다. 등장할 때마다 표시 단계가 올라갈수록(=내부적으로 어려질수록) 조금씩 어려 보이게 묘사하되, 나이나 개월 수를 직접 언급하지 않는다.
  - 플레이어 입장에서는 똘이가 주인공이 아니라서 굳이 그 존재 변화를 눈여겨보지 않는 게 자연스럽다. 표시 12단계부터 똘이가 언급되지 않아도 "반전의 신호"로 읽히면 안 되고, 그냥 "이 게임은 {dog_name}이 주인공이니 똘이가 매번 나오진 않는구나" 정도로 넘어가야 한다. 즉 똘이의 퇴장은 눈에 띄지 않는 배경 디테일로 남아야지, 두 번째 클라이맥스가 되면 안 된다.
- **구현**: 이미 있는 `clue_dependency` 테이블(`murdex-api/domain/story/entities/clue_dependency.py`)로 충분하다. trigger_clue_id="데려오기", trigger_type=INVESTIGATE, effect_type=HIDDEN_TO_FRONT로 target 단서(산책하기·계단오르기)를 연결하면 "조사 시 공개" 연출이 그대로 된다. "{dog_name_2}" 단서는 처음부터 공개 상태(`INITIAL_DISPLAY_STATE = VISIBLE_FRONT`, 이미 있는 단서 초기 상태 옵션)로 두면 된다. 전부 신규 개발이 아니라 기존 기능 설정만으로 되는 부분이다.

### 시각적 반전 장치: 캐릭터 몸 크기 + 털 색깔 (확정안, 13장·프롬프트.txt와 연동)

개는 보통 3살 정도면 성견 크기에 도달하고, 요크셔테리어는 어릴 때 검은 털이 많다가 나이가 들면서 색이 옅어지는 특징이 있다. 이 두 사실로 반전 장치를 심는다. 실제 이미지 생성 프롬프트(`texts/프롬프트.txt`)로 구체화된 최종안은 아래와 같다.

- 내부 시점(실제 나이) 3살~16살 구간은 이미 다 자란 성견이므로 몸 크기가 동일하다. 표시 단계 1~14년(내부 나이 16살~3살, 5장의 공식대로 내부 나이 = 17 − 표시 단계)은 전부 같은 성견 크기로 그린다.
- 표시 단계 15년(내부로는 2살)은 성견 크기의 약 2/3로, 표시 단계 16년(내부로는 1살 = 입양 첫해)은 약 1/2로 작아진다.
- **털 색깔 변화는 이 몸 크기 축소 구간(표시 15~16년)에만 적용한다.** 성견 구간(표시 1~14년)은 색 패턴이 고정("등은 검정, 다리·얼굴은 황갈색, 가슴에 흰 반점")이고, 몸이 작아지는 두 단계에서만 색이 검정 쪽으로 짙어진다 — 2/3 크기(표시 15년)는 "황갈색이 거의 없고 검정이 대부분", 1/2 크기(표시 16년)는 "거의 전부 검정에 가까운 강아지 털"로 프롬프트에 명시돼 있다. 처음 계획했던 "1~16년 전체에 걸친 점진적 색상 그러데이션"보다 범위를 좁혀, 몸 크기 축소와 색 변화를 같은 두 단계에 함께 묶은 것이다.
- **이 장치는 몸 크기 변화가 주력, 털 색깔은 그 위에 얹는 보강 신호다.** 견종 지식이 없어도 "그림 속 개가 갑자기 작아졌다"는 건 누구나 즉시 알아보므로, 몸 크기 변화는 시간 순서 반전(4장)·나이 표기(5장) 다음으로 접근성 높은 두 번째 주력 반전 신호다. 털 색깔이 함께 짙어지는 건 이를 보강하는 역할로, 견종을 아는 플레이어에게는 추가 확신을, 모르는 플레이어에게는 사후 발견의 즐거움을 준다.
- 1/2 크기(표시 16년) 프롬프트에는 "deeply faded, dreamy and misty atmosphere representing an older distant memory"라는 문구도 포함돼 있다. 이건 5장의 이미지 흐림 효과(표시 단계가 올라갈수록 더 오래된 기억이라 흐릿해짐)를 CSS 필터가 아니라 **이미지 생성 단계에서 직접 굽는 방식**으로 구현한 것이다. 12장의 "CSS 필터로 충분하다"는 판단은 이 두 단계(15~16년)에 한해서는 이미지 자체에 흐림/몽환적 분위기를 포함시키는 쪽으로 갱신해야 한다.

### 시각적 반전 장치: 캐릭터 털 길이

몸 크기·색깔과는 별개로, 성견 구간(표시 1~14년)에도 시각적 변화를 준다. `프롬프트.txt`에서 "미용 상태 4단계"로 정리된 것으로, 같은 성견 크기·색 패턴이라도 털 길이를 달리해 단계마다 다른 인상을 준다.

- 4단계: 매우 짧은 털(바리깡으로 민 듯) → 짧은 털(퍼피컷) → 중간 털(자연스럽게 자란 상태) → 긴 털(기본, 가장 풍성).
- 파일럿(표시 1·8·14·16단계)에 적용한 예시: 표시 1년(매우 짧은 털) → 표시 8년(짧은 털) → 표시 14년(중간 털) → 표시 16년(1살, 매우 짧은 털 + 색상·몽환 효과는 위 몸 크기 장치와 결합).
- 이 장치는 견종 지식이 필요 없는 순수한 스타일링 변주에 가깝다. 반전 단서로서의 역할보다는, 3개 화풍 기법을 전환하려던 원안(13장 참고, 이후 단일 화풍으로 단순화됨)을 대신해 단계별로 그림에 시각적 리듬을 주는 역할이 크다.

## 5. 진행 단계 구조

- 총 16개 조사 단계 (강아지가 실제로 산 16년에 대응) + 도입 단계.
- 단계명은 표면적으로 "0년(도입) → 1년 → 2년 → ... → 16년"으로 위로 올라가는 것처럼 보이지만, 실제 내부 시점(내용)은 반대로 흐른다.

| 표시 단계 | 플레이어 체감 | 실제 내부 시점 (내용) |
|---|---|---|
| 0년 (도입, 타이머 없음) | 시작 화면 | 이별 후, 지금 |
| 1년 | "이제 1년차구나" | 마지막 해 (16살, 노견) |
| 2년 | | 15살 |
| ... | | ... |
| 15년 | | 2살 |
| 16년 (마지막 조사 단계) | "16년차, 끝났나?" | 1살 = **입양 첫해** → 여기서 반전 공개 |

> 확인 필요: 사용자 메모에 "0년(시작 단계)"과 "16년까지"가 함께 언급되어 있는데, 이를 17개로 셀지 위 표처럼 "0년=도입(타이머 없음) + 1~16년=16개 조사 단계(각 5분)"로 셀지 정리가 필요하다. 후자로 해석하면 7번 항목의 "16단계=80분"과 정확히 맞아떨어지므로, 이 해석을 기본안으로 제안한다.

- 각 단계 5분, 시간 초과 시 강제로 다음 단계로 진행. 5분을 다 안 써도 원하면 일찍 다음 단계로 넘어갈 수 있다(강제 진행은 "5분을 넘길 수 없다"는 상한이지, "5분을 채워야 한다"는 하한이 아님).
  - 상징적 의미(세월은 붙잡을 수 없다)는 매우 좋다.
  - **의도된 장치**: 초반(내부로는 마지막 나날) 단계는 단서가 2~3개뿐이라 1분도 안 돼 다 보고 일찍 넘길 수 있다. 이건 버그나 페이싱 문제가 아니라, 반전을 깨달은 뒤 플레이어 스스로 "그때가 사실 개와 함께한 마지막 시간이었는데, 나는 그걸 그냥 스쳐 지나갔구나"라는 후회를 느끼게 만드는 핵심 장치다. 콘텐츠 분량(초반 단서 적음)과 진행 방식(조기 스킵 허용)이 결합해서, 플레이어의 실제 행동(빨리 넘긴 것) 자체가 나중에 후회의 대상이 되는 구조다.
  - 10장의 역순 일기장과 직접 연결된다. 만약 플레이어가 초반 단계에서 조사를 거의 안 하고 넘어갔다면, 일기장에서 해당 구간(실제로는 마지막 나날)이 유독 비어 있거나 짧게 나올 것이다. 이 "빈 페이지"가 억지로 채워지지 않고 그대로 드러나야 후회가 구체적으로 와닿으므로, 일기장은 실제로 한 행동만 정직하게 반영해야 한다(부족한 구간을 자동으로 채우거나 미화하면 안 된다).

## 6. 조사 시스템: 단서 = 함께한 행동, AP = 그 주의 예산

- 단서는 정보가 아니라 **강아지와 함께한 행동**(안아주기, 산책하기 등)을 의미한다.
- AP는 화면에 숫자/게이지로 노출한다. 게임을 하는 동안은 그냥 "이 단계에서 쓸 수 있는 자원" 정도로만 읽히게 두고, AP의 진짜 의미(예산 7이 사실 "그 해의 어느 한 주"를 뜻한다는 것)는 나중에(11장 아웃트로에서) 밝혀진다. **AP는 "마음의 크기" 같은 감정적 의미를 갖지 않는다** — 아래 "단서/AP 곡선" 절 참고. 감정("건강했을 때 마음을 다 못 썼다" 등)은 숫자로 증명하려 하지 않고 11장에서 작가가 직접 말로 풀어준다.
  - 이 설계는 4장의 반전과 결이 비슷하다. 4장에서는 "단계 숫자"가 사실 반대 방향이었다는 게 뒤늦게 드러나고, 여기서는 "AP 7"이 사실 게임 자원의 상한이 아니라 "그 해의 어느 한 주"라는 시간틀이었다는 게 뒤늦게 드러난다. 다만 두 반전은 종류가 다르다 — 표시 단계 반전은 "이야기의 방향"에 관한 것이고, AP 반전은 "숫자의 정체"에 관한 것이라 서로 다른 "아, 그랬구나"를 준다.
  - **구현 관점 정정**: 처음 검토했을 때는 AP를 신규 UI로 봤는데, 실제로는 murdex에 이미 완성된 "AP(액션 포인트)" 시스템이 있다(`ApTracker` 컴포넌트, `step_role_ap` 테이블로 **단계별·역할별 최대 AP를 크리에이터 UI에서 그냥 숫자로 설정**하는 기능). 즉 6장의 AP 시스템 전체는 **신규 개발이 전혀 필요 없고, 크리에이터 도구에서 단계별 숫자만 입력하면 되는 기존 기능**이다. 게이지 표시 UI도 이미 있다.
  - **재정정: 별도 "액션" 카탈로그는 쓰지 않는다.** 처음엔 `role_action`(작가가 "안아주기"·"산책하기" 같은 이름으로 별도 액션을 정의하는 테이블)을 AP 소비 수단으로 봤는데, 이러면 단서(2개)와 액션(N개)이 별개 목록으로 나뉘어 "이 단계에서 총 몇 번의 행위를 한다"는 수가 부풀려지고 6장의 "단서 수 = 함께한 행동의 수"라는 원칙과 어긋난다. **실제로는 `clue` 엔티티 자체에 `ap_cost` 필드가 있다** — 단서 하나하나가 곧 조사(투자)할 때 AP를 소모하는 행위이고, 별도 액션 목록이 필요 없다. `step_role_ap.max_ap`는 그 단계에서 쓸 수 있는 AP 예산이고, 단서별 `ap_cost`는 기본적으로 전부 1로 고정한다(확정안은 아래 "단서/AP 곡선" 참고).

### 비주얼 톤 적용 범위 (변경 규모 판단)

murdex의 작품 이용 화면은 기본적으로 느와르 톤(어두운 배경, `bg-zinc-950`류)이며, 이건 헤더/사이드바/버튼 같은 공용 UI 프레임에 플랫폼 차원에서 고정돼 있다. 반면 본문 텍스트 영역(`.story-content`)은 작품마다 자기만의 CSS를 갖는 게 이미 표준 방식이다(도플로이드도 `styles/도플로이드.css`로 이 영역만 커스텀).

- **기본안(변경 규모 작음)**: 본문/단서 카드 영역만 밝고 따뜻한 톤으로 커스텀 CSS를 새로 만든다. 기존 작품들과 동일한 방식이라 추가 개발 없이 CSS 파일 하나로 끝난다. AP 표시도 이 영역 안에서 다룬다.
- **바깥 UI 프레임(헤더, 버튼, 사이드바, 모달)은 손대지 않는다.** 이론적으로는 작품별 CSS를 페이지에 통째로 주입하는 구조라 이 영역도 덮어쓸 수는 있지만, 지금까지 어떤 작품도 시도한 적 없는 영역이고, 저 클래스들은 페이지 전반에서 공용으로 쓰여서 하나 덮어쓰면 아이콘 대비·호버 상태 등 의도치 않은 곳까지 같이 바뀔 위험이 있다. 손대려면 게임 화면 전체를 하나하나 QA해야 해서 작업 규모가 커진다.
- 결론: 프레임(느와르)은 액자로 남기고, 본문(따뜻함)만 바꾸는 쪽을 기본안으로 잡는다. 프레임까지 바꾸는 건 검증된 적 없는 영역이라 하고 싶다면 별도 2차 개선 단계로 미룬다.

### 단서/AP 곡선 (확정안: 예산 고정 + 단서당 비용 고정)

- **AP 예산(`step_role_ap.max_ap`)은 모든 단계에서 동일하게 7로 고정한다.** 단, 이 "7"은 감정("마음의 크기")을 상징하는 숫자가 아니다. **그냥 "그 해의 어느 한 주(7일)"라는 시간틀일 뿐이다.** 각 조사 단계는 그 해에 있었던 일 중 특정 한 주를 들여다보는 것이라는 설정이다.
- **이 "일주일" 설정 때문에, 한 단계 안의 모든 "생전" 단서 날짜는 실제로 7일 이내에 모여 있어야 한다.** 예를 들어 표시 1단계(마지막 해)는 사망일이 그 주의 마지막 날이므로, 유효 날짜 범위가 자동으로 정해진다(사망일이 8월 21일이면 8월 14일~8월 21일). 4장의 "데려오기"류 구조적 단서는 이 규칙에서 예외다 — 애초에 "그 해에 있었던 일"이 아니라 시간상 완전히 다른 시점(사후)에 벌어진 사건이기 때문이다.
- **단서 하나당 AP 비용(`clue.ap_cost`)은 기본적으로 전부 1로 고정한다.** (예외: 구조적 잠금해제 단서는 0으로 둔다 — "함께한 행동"이 아니라 서사 진행용 단서라서.)
- 이렇게 하면 별도로 "AP 수 곡선"을 따로 설계할 필요가 없어진다. **그 단계에서 실제로 쓸 수 있는 최대 AP는 그 단계의 단서 개수와 같아진다**(단서 수 × 1 ≤ 7). 예산 7 중 실제로 쓸 수 있는 만큼만 쓰고 나머지는 항상 남는데, **이 "남는 AP"에 "마음의 크기" 같은 감정적 의미를 억지로 붙이지 않는다.** 그냥 "그 주에 함께할 거리가 그만큼 있었다/없었다"는 구조적 사실로만 다룬다. "건강했을 때 마음을 다 못 썼다" 같은 정서적 해석이 필요하면, 그건 게임 숫자로 증명하려 하지 말고 11장 아웃트로에서 작가가 직접 말로 풀어준다.
  - 표시 1단계(단서 2개): 최대 2 AP 사용 가능, 5 AP는 쓸 곳이 없어 항상 남는다. 그 주에 함께할 수 있었던 일이 두 가지뿐이었다는 뜻이다.
  - 표시 8·14단계(단서 4~5개): 최대 4~5 AP 사용 가능, 2~3 AP가 남는다.
  - 표시 16단계(단서 2개, 아직 성견이 안 된 시기): 다시 최대 2 AP로 줄어든다.
- 이 "구조적으로 못 쓰는 AP"(단서 수가 적어서 원천적으로 못 쓰는 몫)와는 별개로, **플레이어가 있는 단서를 다 조사하지 않아서 생기는 "행동으로 못 쓴 AP"**가 한 겹 더 있다. 전자는 작가가 곡선(단서 수)으로 설계하는 몫이고, 후자는 5장의 조기 스킵 장치와 9장의 "머문 시간·AP 사용량" 규칙이 담당하는 플레이어 행동의 몫이다. 두 층이 합쳐져 최종적으로 "AP 7 중 몇을 썼는가"라는 하나의 숫자가 된다 — 이 최종 숫자를 플레이어별로 다르게 해석하는 건(9장 규칙) 여전히 유효하다. 다만 "예산 7 자체"에는 의미를 붙이지 않는다는 게 이번에 정리된 원칙이다.
- 단서 수 자체의 곡선(U자형: 낮음 → 높음 → 다시 낮음)은 기존 설계 그대로 유지한다. 예시 표:

| 조사 단계 | 내부 시점(나이) | 단서 수 (예시) | 예산 | 구조적으로 남는 AP |
|---|---|---|---|---|
| 1 | 16살 | 2 | 7 | 5 |
| 2~4 | 13~15살 | 3 | 7 | 4 |
| 5~10 | 7~12살 | 4~5 | 7 | 2~3 |
| 11~14 | 3~6살 | 5~6 | 7 | 1~2 |
| 15~16 | 1~2살 | 2~3 | 7 | 4~5 |

- 이 확정안은 크리에이터 화면 설정도 더 단순하게 만든다. `step_role_ap.max_ap`를 16단계 전부 7로 똑같이 넣고, 단서마다 `ap_cost`를 1(구조적 잠금해제 단서만 0)로 넣으면 끝난다.

## 7. 톤 앤 매너

- 전체 분위기는 밝고 따뜻하게. 초반(내부로는 임종에 가까운 시기)도 슬프지 않고 밝게 그려서, 플레이어는 그냥 "새끼강아지가 이제 막 자라는구나" 정도로 착각하게 만든다.
- 단서 텍스트는 수식어 없이 건조하게 서술. "몸이 약하고 힘이 없다"(O) / "아프고 늙어서 몸이 약하고 힘은 예전 같지 않다"(X). 노쇠·질병을 직접 명시하는 수식어를 빼야 초반 단계에서 "이게 임종 직전이다"라는 걸 숨길 수 있다.
- 이 원칙은 [단서 관찰 페어플레이 규칙](feedback_clue_fairplay_observability.md)과 방향은 같지만 이유는 다르다. 원래 규칙은 "역할이 검증 못하는 해석을 작가가 단정하면 안 된다"는 것이었는데, 여기서는 "해석이 가능한데도 반전을 위해 의도적으로 생략한다"는 쪽이다. 즉 이 작품은 정보를 숨기는 게 아니라 **정서적 색채(늙음/쇠약이라는 인상)를 숨기는 것**이므로, 사실 자체는 다 줘도 되지만 그 사실에 붙는 형용사와 톤을 철저히 편집해야 한다는 뜻으로 이해했다.
- **서술 시점: 주인이 그날 있었던 일을 적은 1인칭 관찰 기록.** 단서 내용은 개의 행동을 3인칭으로 요약("몸이 약하고 힘이 없다")하는 게 아니라, 주인이 직접 겪은 순간을 서술하는 형태로 쓴다("{dog_name}를(을) 데리고 산책을 나섰다. {dog_name}는(은) 곧잘 따라오다가 안아달라고 한다..."). 개가 왜 그런 행동을 하는지는 절대 설명하지 않고 행동만 관찰해서 남긴다 — 이러면 플레이어는 그 이유를 스스로(잘못) 채워 넣게 된다. 초반(내부로는 노년기) 단계에서 "안아달라고 한다", "계단 앞에서 멈췄다" 같은 문장은 노령으로 인한 체력 저하이지만, 원인을 말하지 않으므로 플레이어는 "아직 어려서 그런가보다"로 자연스럽게 착각한다. 이게 이 작품의 핵심 서술 트릭이다. 표시 16단계(9장, 반전 공개)에 가서야 이 트릭이 풀린다.
- 이 서술 방식은 10장의 일기장·편지와도 구조적으로 맞물린다. 단서는 "주인이 남긴 관찰 기록"이고, 엔딩의 일기·편지는 그 기록을 "개의 목소리로 다시 들려주는 것"이다. 같은 사건을 두 개의 다른 1인칭 시점(주인 → 개)으로 두 번 말하는 셈이다. 이 작품은 이렇게 **플레이 중(주인이 개에 대해 쓰는 일기) ↔ 엔딩(개가 주인에게 쓰는 일기·편지)**이라는 대칭 구조를 이룬다.
- **단서명·단서 내용도 "플레이어가 쓰는 일기"처럼 보이게 한다.** 단서명은 "{표시 연도}년: {행동}" 형식(예: "1년: 산책하기")으로 써서 일기 페이지 제목처럼 보이게 하고, 단서 내용은 맨 앞에 "O월 O일, 날씨." 형식의 일기 헤더를 붙인다(예: "8월 20일, 맑음. {dog_name}를(을) 데리고 산책을 나섰다..."). 날짜 자체가 실제 캘린더와 맞아야 하는 건 아니고, 일기라는 느낌을 주기 위한 장치다.
- **[단계 설명] 필드는 서사가 아니라 게임 가이드다.** "{dog_name}와(과) 오늘 있었던 일을 적는다" 같은 서사적 문장을 넣으면 안 된다. 이 자리는 "이번 단계에서 무엇을 하면 되는지"(단서 조사, AP 상한, 시간제한 등)를 안내하는 실용적인 문구로 채운다. 서사(반전 포함)는 전부 단서명·단서 내용 쪽에서 담당한다.

## 8. 개인화 시스템: 강아지 이름 치환

- 시작 직전(또는 작가가 지정한 임의의 단계에서) "당신의 강아지 이름은?" 같은 플레이어 친화적 문구로 입력받는다(기본값 "아리"). 입력하면 작품 전체에서 그 이름으로 표시된다.
- **작가가 콘텐츠에 쓰는 실제 문법**: 변수명과 조사를 한 토큰으로 같이 쓴다. 예: `{dog_name}는(은) 혀를 내밀었다`. 렌더링될 때는 `{dog_name}` 자리에 실제 입력값(예: "아리")이 들어가고, `는(은)` 중 입력값의 받침 유무에 맞는 하나만 남아 최종적으로 "아리는 혀를 내밀었다"로 보여야 한다. 플레이어에게 "dog_name 입력해주세요" 같은 내부 변수명이 노출되면 절대 안 되고, 항상 작가가 설정한 자연스러운 문구("당신의 강아지 이름을 입력해 주세요")로 보여야 한다.
- **입력 시점은 작품마다 다를 수 있다.** 앙코르는 시작(0년) 단계가 자연스럽지만, 다른 작품은 시작이 아닌 중간 단계에서 개인화 정보를 받고 싶을 수 있다. 그래서 이건 앙코르 전용 하드코딩이 아니라 **어느 단계에든 붙일 수 있는 플랫폼 범용 기능**으로 설계해야 한다.
- **구현 관점 (재검토 결과, 처음 생각보다 재사용 여지가 큼)**: 입력을 "받는" 부분은 사실 새로 만들 필요가 없을 가능성이 높다. 기존 `Question` 엔티티(`murdex-api/domain/story/entities/question.py`)가 이미 `step_id`(어느 단계에든 붙일 수 있음)와 `is_multiple_choice`(false면 주관식/자유 입력)를 갖고 있다. 즉 "주관식 질문"을 원하는 단계에 하나 배치하고, 질문 문구(`title`)를 "당신의 강아지 이름을 입력해 주세요"로 작가가 직접 쓰면, 입력 UI·저장(`room_answer`)까지 기존 질문/답변 시스템을 그대로 재사용할 수 있다. 이러면 "플레이어 친화적 문구로 입력받아야 한다"는 요구도 자동으로 만족된다(작가가 쓰는 `title`이 그대로 보이는 문구이므로).
- **진짜 새로 만들어야 하는 부분은 두 가지뿐이다.**
  1. 특정 질문의 답변을 "치환 변수"로 지정하는 연결고리. `Question` 엔티티에 `variable_key`(예: `dog_name`) 같은 선택적 필드를 추가해서, 이 질문의 주관식 답변이 곧 `{dog_name}`로 쓰인다는 걸 작가가 크리에이터 화면에서 지정할 수 있어야 한다.
  2. 실제 치환 엔진: 서버가 단계/단서 HTML을 응답으로 만들어 내려줄 때, `{변수명}` 및 `{변수명}조사1(조사2)` 패턴을 찾아 값과 올바른 조사로 바꿔주는 로직. 조사 판별(은/는, 이/가, 을/를, 와/과)은 유니코드 종성 유무만 보면 되는 잘 알려진 로직이다.
- 이름 입력에 특수문자·과도한 길이 등 예외 처리도 필요하다(이것도 기존 질문 답변 검증 로직에 규칙을 하나 추가하는 수준으로 될 가능성이 높다).
- **변수가 여러 개여도 같은 방식으로 확장된다.** 4장에서 다루는 둘째 강아지(똘이, `{dog_name_2}`)처럼 이름이 두 개 이상 필요해지면, `variable_key`가 다른 `Question`을 하나 더 배치하면 된다. 치환 엔진·조사 처리 로직은 변수 개수와 무관하게 그대로 재사용된다.
- **구조적 반전 장치: "첫 번째/두 번째" 입력 순서.** 실제 입력 문구는 "당신의 강아지 이름은?" 하나가 아니라, 시작 단계에서 연달아 두 개를 받는다: "첫 번째 강아지 이름을 알려주세요"(`{dog_name}`, 기본값 "아리") → "두 번째 강아지 이름을 알려주세요"(`{dog_name_2}`, 기본값 "똘이", 비워두면 기본값 적용).
  - 이 "첫 번째/두 번째"라는 순서 자체가 진짜 사실이다 — {dog_name}(아리)이 실제로 먼저 있던 개고, {dog_name_2}(똘이)는 나중에 태어난 개다.
  - 그런데 4장의 "데려오기" 단서는 정반대 인상을 준다 — {dog_name_2}(똘이)가 이미 집에 있던 개이고 {dog_name}(아리)이 새로 들어오는 개처럼 읽힌다. 그래서 플레이어는 "기존에 있던 강아지가 있는데 왜 새로 온 애가 첫 번째지?" 하고 잠깐 의아할 수 있는데, "아마 이 작품의 주인공이라 첫 번째인가 보다" 정도로 대수롭지 않게 넘어가게 된다.
  - 즉 이 입력 폼은 아무 의심도 사지 않는 지극히 평범한 UI 문구("반려동물이 여러 마리면 순서대로 입력해주세요" 수준) 안에, 사실 게임 전체의 진짜 관계(누가 먼저였는지)를 아무도 눈치채지 못하게 처음부터 밝혀두는 자리다. 4장의 "데려오기" 서술 트릭과 정확히 반대 방향의 인상을 주면서도, 둘 다 거짓말은 하지 않는다는 점이 핵심이다(입력 순서도 진짜, "데려오기" 문장도 관찰된 사실 그대로).
  - 구현은 두 `Question`을 같은 단계(시작 단계)에 `question_order` 1, 2로 배치하면 끝난다. 신규 개발 없음.
- **다른 작품의 기존 질문·답변에 대한 영향(확인 완료)**: 영향 없다. 이유는 두 가지다. (1) 질문·엔딩 규칙·답변이 전부 `story_id` 기준으로 조회되도록 이미 짜여 있다(`CalculateEndingUseCase`가 `get_by_story_id`로 조회하는 걸 확인함) — 앙코르에서 새로 만드는 질문은 앙코르 스토리에만 속하고 다른 작품의 질문 목록에는 아예 나타나지 않는다. (2) `variable_key`는 nullable 컬럼으로 추가되므로 기존 질문들은 전부 `NULL`을 갖고, 치환 로직은 이 값이 설정된 질문에서만 동작한다 — 다른 작품 질문은 이 값이 없으니 치환 로직 자체가 실행되지 않는다. 이런 "nullable 필드 추가로 안전하게 확장" 패턴은 도플로이드의 `min_hand_limit` 기능 때도 이미 쓴 방식이라 낯설지 않다.

**역할(Role) 정보 작성 방침(2026-08-25)**: 이름 개인화와 같은 맥락의 문제 — 플레이어가 "역할을 맡는다"가 아니라 "이게 바로 나"라고 느껴야 한다. `RoleManager`가 요구하는 역할 이름/공개 정보/비공개 정보/역할 이미지를 그대로 채우면 오히려 캐릭터가 생겨버려 몰입이 깨진다. 확정한 방침: (1) 역할 이름은 고유명사 대신 관계어 "강아지의 주인"(7장에서 이미 확립한 1인칭 "주인" 시점과 통일). (2) 공개 정보는 "왜 신상 정보가 없는지"를 직접 설명하는 2인칭 문구로 채운다 — 다른 작품들처럼 이름/나이/직업이 나올 거라 기대하고 왔다가 없으면 버그처럼 보일 수 있어서, 여기서만 예외적으로 살짝 4th wall을 건드린다. (3) 비공개 정보는 비워둔다 — 원래 "다른 플레이어에게 숨기는 내 비밀"용인데 1인용이라 숨길 대상이 없고, 억지로 채우면 반전이 있다는 느낌만 준다. (4) 역할 이미지는 사람 얼굴 대신 목줄을 쥔 손만 보이는 상징적 이미지로 최소화 — 지금까지의 캐릭터 아트가 전부 강아지 단독 기준(`프롬프트.txt`)이라 사람 얼굴을 새로 열면 스코프가 커진다는 판단(13장 표지 이미지 논의와 같은 이유). 실제 문구와 이미지 프롬프트는 `texts/역할.txt`, `texts/프롬프트.txt` "7. 역할 이미지 프롬프트" 참고. `RoleActionManager`/`RoleSecretManager`(범인 미스터리용 액션·비밀 시스템)는 이 작품에 해당 사항이 없어 비워둔다.

## 9. 미스터리 장치: 아주 쉬운 주관식 퀴즈

- 최종(내부 시점상 입양 첫해) 단계에서 "{dog_name}를(을) 위해 준비한 강아지 케이크입니다. 몇 개의 초를 꽂아야 할까요?" 같은 질문.
- 눈치가 빠르면 1개(반전을 이해했다면), 아니면 다른 숫자.
- 오답이어도 엔딩에 큰 영향 없음.
- 이 설계는 정확한 판단이라고 본다. 이 작품은 정답을 맞히는 쾌감이 아니라 "아, 그랬구나" 하고 스스로 깨닫는 순간이 핵심이라, 퀴즈를 게이트로 걸면 오히려 감정선을 끊는다. 오답 허용 + 무영향은 옳은 선택.

## 10. 엔딩: AI가 쓰는 역순 일기장 + 무지개다리 편지

- 단서(=함께한 행동) 내용을 그대로 나열하는 게 아니라, 획득 순서의 역순으로 GPT에 전달해 **"개가 사람에게 남기는 일기"** 형식의 글로 새로 생성한다. 마지막에는 강아지별에서 개가 보내는 **편지**를 한 편 더 생성해 보여준다.
- 획득 순서를 역순으로 넣으면 결과물은 자연히 "입양일 → 마지막 날"이라는 정상적인 시간 순서로 쓰인 일기가 된다. 엔딩이 이 작품의 핵심 구조(거꾸로 흐르던 시간을 마지막에 바로잡는다)를 한 번 더 반복하는 셈이라 구조적으로 잘 맞는다. 원본 단서 문장을 그대로 붙여넣는 것보다 훨씬 감동적일 것이라는 판단에 동의한다 — 건조하게 쓰인 단서 텍스트(7장)를 개의 목소리로 다시 풀어내면, 사실을 감정으로 번역하는 과정 자체가 하나의 연출이 된다.

### 구현 방식: 전용 화면 (기존 사례와 동일한 패턴)

이 작품에서 사용자가 언급한 대로, [도플로이드](works/도플로이드) 소장 심문이나 [바스타즈 오브 더 유니버스](works/바스타즈 오브 더 유니버스) 엔딩 판정 툴과 같은 방식(게임 화면과 분리된 전용 페이지를 만들어 iframe으로 임베드)이 그대로 적용 가능하다. 실제 코드로 확인한 결과다.

- `murdex-web/app/tools/doploid/interrogation/page.tsx` — 도플로이드 소장 심문 전용 페이지. `window.parent`를 통해 같은 오리진의 게임 화면에서 roomId/stepId를 읽어오고, 자체 API(`interrogationApi`)로 서버와 통신한다.
- `murdex-web/app/tools/bastards-of-the-universe/calculator/` — 바스타즈 엔딩 판정 툴, 같은 패턴.
- `murdex-api/infrastructure/external/openai_service.py` — GPT 연동이 이미 범용 래퍼(`OpenAIService.chat()`, 모델은 `gpt-4o-mini`)로 구현돼 있고, 현재는 소장 심문 전용 엔드포인트(`/doploid/ask`)에서만 쓰인다. 이 클래스 자체는 재사용 가능한 구조라, 앙코르는 같은 서비스를 새 엔드포인트에서 새 프롬프트로 부르기만 하면 된다.

즉 앙코르의 일기장도 `murdex-web/app/tools/encore/diary/page.tsx`(가칭) 같은 전용 화면 + 새 백엔드 엔드포인트(기존 `OpenAIService` 재사용) + 기존에 이미 있는 `room_clue_ownership.acquired_at`(단서별 획득 시각) 데이터를 조합하면 된다. 오히려 소장 심문보다 구현이 단순하다. 소장 심문은 페르소나·질문 횟수 제한·대화 이력 저장까지 갖춘 멀티턴 챗봇인데, 일기장은 정해진 자료를 한 번(또는 두 번: 일기 + 편지) 모아서 생성하는 원샷 생성이라 상태 관리가 훨씬 적다.

### 짚어야 할 리스크

- **톤 이탈 위험**: GPT 기본 출력은 이 프로젝트의 문체 규칙(em-dash 금지, 상투적 표현 금지, 담백한 문장)과 어긋나기 쉽다. 시스템 프롬프트에 문체 규칙을 명시하고, 실제로 몇 번 생성해보며 튜닝하는 과정이 필요하다.
- **없는 기억을 지어내면 안 됨**: 플레이어가 초반(=실제로는 마지막 나날) 단계에서 조사를 별로 안 했다면, 그 시기의 원재료가 거의 없다. 이때 GPT가 빈 곳을 그럴듯하게 지어내 채우면 5장에서 설계한 "빈 페이지가 곧 후회"라는 장치가 무너진다. 프롬프트에 "주어진 기억 밖의 내용을 지어내지 말 것, 부족하면 부족한 대로(예: 짧게, 흐릿하게) 써라"를 명시해야 한다. 이 제약이 오히려 후회의 장치를 더 정확하게 살려준다.
- **로딩 UX**: GPT 생성은 즉시 끝나지 않는다. "기억을 모으는 중입니다..." 같은 연출로 대기시간 자체를 감정적 여운으로 바꿀 수 있다.
- **비용/난이도**: gpt-4o-mini로 완주당 1~2회 호출이라 비용은 사실상 무시할 수준. 콘텐츠 조절(모더레이션) 이슈도 거의 없다 — 사용자 자유 입력이 아니라 작가가 쓴 단서 텍스트를 재료로 쓰는 구조라서, 소장 심문(플레이어가 임의로 입력하는 질문에 응답)보다 오히려 통제하기 쉽다.

## 11. 아웃트로: 작가의 말 (기믹 해설)

역행 구조를 설계한 실제 동기는, 아리를 보내고 나서 사용자 자신이 처음 아리가 집에 온 날로 돌아가고 싶다는 마음이 너무 컸기 때문이다. 이 동기는 게임 진행 중에는 드러낼 필요가 없지만, 엔딩(10장의 역순 일기장) 다음에 이어지는 **아웃트로**에서 플레이어에게 직접 해설하는 형태로 들어가야 한다.

- 위치: 역순 일기장 엔딩이 끝난 직후, 별도의 화면(작가의 말/에필로그 성격).
- 내용 방향: "왜 시간을 거꾸로 진행시켰는가"를 1인칭으로 풀어준다. 예를 들어 "이 작품은 {이름}를 보내고 나서, 다시 처음 그 날로 돌아가고 싶었던 마음에서 시작했습니다" 같은 톤. 플레이어가 방금 겪은 반전(마지막 단계에 가서야 이게 입양일이었다는 걸 깨닫는 경험)이, 사실은 작가 자신이 상실 후 실제로 느낀 감정을 플레이어에게 그대로 체험시킨 장치였다는 걸 알려주는 구조다.
- 이 아웃트로는 10장의 "역순 일기장"과 역할이 다르다. 일기장은 **아리와 함께한 시간을 다시 순서대로 보여주는 장치**(체험의 결과물)이고, 아웃트로는 **왜 이런 구조로 만들었는지 작가가 직접 말을 거는 장치**(체험 이후의 해설)다. 순서상 일기장 → 아웃트로로 배치하면, 플레이어는 먼저 감정적으로 정리된 시간을 보고 난 뒤에 "이게 사실 이런 마음에서 나온 구조였구나"라는 걸 한 번 더 이해하게 된다.
- 이 해설이 들어가면 반전의 의미가 "아, 시간이 거꾸로였네"라는 구조적 재미에서 그치지 않고, "이건 작가가 실제로 느낀 그리움을 플레이어에게 나눠준 것"이라는 무게로 바뀐다. 좋은 마무리 방향이라고 본다.
- **이스터에그 해설 추가**: 8장의 "첫 번째/두 번째 강아지 이름" 입력 순서에 숨겨둔 진짜 의미(입력 순서는 사실 그대로였다는 것, "데려오기" 단서가 준 인상과 실제로는 반대였다는 것)도 여기서 짚어주면 재밌다. 눈치채지 못했던 플레이어에게는 "아, 그래서 첫 번째였구나" 하는 뒤늦은 발견을, 눈치챈 플레이어에게는 확인의 재미를 준다.
- **초안 작성 완료**: `texts/아웃트로.txt`의 "1. 작가의 말" 섹션 참고(별도 파일이 아니라 아웃트로 파일 안의 한 섹션이다 — 아웃트로에 다른 내용이 추가될 수 있어 이렇게 구조를 잡았다). 아리·AP의 진짜 의미·"첫 번째/두 번째" 이스터에그까지 짧게 담았다. 이 텍스트는 {dog_name} 같은 치환 변수를 쓰지 않고 실제 이름("아리", "똘이")을 그대로 쓴다 — 플레이어가 자기 아이 이름으로 겪은 이야기가 사실은 작가 자신의 진짜 이야기였다는 걸 여기서 처음 밝히는 구조이기 때문이다.
- **기술적 구현 방식 정정(2026-08-25)**: 한때 이 아웃트로를 일기장·편지처럼 `app/tools/encore/diary` 안의 독립 프론트엔드 페이지로 만들 계획이었으나, **아니다 — 아웃트로는 독립 페이지가 아니라 기존 방식(일반 HTML 콘텐츠) 그대로 쓴다.** 실제로 `GameEndingView.tsx`를 코드로 확인해보니, 플랫폼에 이미 "공통 아웃트로(에필로그)" 기능이 완성돼 있다: 마지막 단계(`isFinalStep` 또는 `stepType === ENDING/EPILOGUE`)의 **`Step.outro` 필드**(크리에이터 화면 `StepManager.tsx`에 이미 있는 "아웃트로 내용을 작성하세요" QuillEditor 입력란)에 HTML을 써넣으면, 모든 엔딩 대본을 다 읽은 뒤 자동으로 "에필로그" 섹션으로 렌더링된다(`outroHtml`, `GameContentStyle`로 같은 customCss가 적용됨). 즉 **아웃트로는 신규 개발이 전혀 아니라, 이미 있는 필드에 콘텐츠만 채워 넣으면 되는 항목**이다 — 12장·15장의 관련 서술도 이에 맞춰 정정함.

## 12. 신규 개발이 필요한 기능 정리

기존 시스템으로 되는 것과 새로 만들어야 하는 것을 나눠서 정리한다.

**기존 기능으로 완전히 커버됨 (신규 개발 불필요)**
- 1인용 진행, 단계별 단서 배치/공개, 단계 전환 — 기존 스토리/단계 시스템 그대로 사용 가능.
- **AP 시스템 전체** — `step_role_ap` 테이블이 단계별·역할별 최대 AP(예산 상한)를 이미 지원하고, `ApTracker` 컴포넌트가 게이지/숫자 UI까지 갖추고 있음. AP 소비는 별도 액션 카탈로그가 아니라 `clue.ap_cost`(단서 자체에 붙은 AP 비용)로 처리한다 — 단서 하나하나가 곧 "함께한 행동"이자 AP를 쓰는 행위이고, 조사할 때 그만큼 AP가 깎인다. 크리에이터 화면에서 단계별 AP 상한과 단서별 AP 비용만 입력하면 끝남.
- 단서 획득 순서 데이터 — `room_clue_ownership` 테이블에 단서별 `acquired_at`(획득 시각)과 `acquired_method`가 이미 기록됨. 일기장에 필요한 원본 데이터는 이미 존재함.
- **단서 잠금해제(조사 시 다른 단서 공개)** — `clue_dependency` 테이블이 이미 있음(trigger_clue_id/trigger_type=INVESTIGATE/target_clue_id/effect_type=HIDDEN_TO_FRONT). 4장의 "데려오기 조사 → 산책하기·계단오르기 공개" 연출을 그대로 구현할 수 있는 기존 기능. 크리에이터 화면에서 연계만 설정하면 끝남.
- GPT 연동 인프라 — `openai_service.py`의 `OpenAIService`가 이미 프로덕션에서 검증된 범용 래퍼(gpt-4o-mini)로 존재함. 새 프롬프트로 새 엔드포인트에서 재사용만 하면 됨.
- 전용 화면(iframe 툴) 구축 패턴 — `app/tools/도플로이드/interrogation`, `app/tools/바스타즈-오브-더-유니버스/calculator` 두 사례로 이미 검증된 구조. `app/tools/encore/diary`도 같은 패턴으로 만들면 됨.
- **단계별 시간제한 + 자동 진행 기본 골격** — 처음엔 이 부분을 "확인 필요"로 남겨뒀는데, 실제로 확인해보니 생각보다 훨씬 많이 이미 있었다. `story_step.estimated_duration`(단계별 배정 시간, 분 단위 — 원래는 시간 기반 자원 시스템의 일부였다가 AP 시스템으로 전환된 뒤에도 "실제 플레이 타임 가이드"로 남겨둔 필드다, `20260127_convert_time_to_ap_system.sql` 참고), `story_step.is_auto_proceed`(수동/자동 진행 선택, 크리에이터 화면 `StepManager.tsx`에 "자동 진행 (시간/조건)" 옵션으로 이미 노출돼 있음 — 사용자가 기억한 "단계 편집의 강제 진행"이 바로 이것), `room.current_step_started_at`(현재 단계 시작 시각)이 이미 `sync_game_state_use_case.py`(`stepDuration`/`currentStepStartedAt`으로 프론트에 전달)와 `progress_step_use_case.py`(`is_auto_proceed` 체크)에 실제로 쓰이고 있다. 즉 "단계별로 배정 시간을 정하고, 시간이 다 되면 자동으로 다음 단계로 넘어간다"는 기본 동작은 **크리에이터 화면에서 배정 시간(5분)과 자동 진행 여부만 설정하면 되는 기존 기능**이다.
- **질문(Question) 시스템의 주관식 지원** — `Question` 엔티티(`is_multiple_choice: bool`)가 `false`일 때 주관식(자유 입력) 질문이 되고, `step_id`를 가지고 있어 **어느 단계에든** 배치할 수 있다. 9장의 케이크 초 개수 퀴즈뿐 아니라, 8장의 이름 입력도 이 시스템을 그대로 재사용할 수 있다(아래 참고).

**신규 개발 필요 (실제로 새로 만들어야 하는 것)**
1. **개인화(이름 치환)** — 재검토 결과 처음 생각보다 범위가 좁아졌다. 입력을 "받는" 부분은 기존 질문 시스템(위 참고)을 재사용하면 되므로 새로 만들 것이 없다. 진짜 신규는 두 가지뿐이다: (a) `Question`에 `variable_key` 같은 선택적 필드를 추가해 "이 질문의 답을 치환 변수로 쓴다"는 걸 작가가 지정하는 연결고리, (b) 콘텐츠 HTML에서 `{변수명}` 및 `{변수명}조사1(조사2)`(예: `{dog_name}는(은)`) 패턴을 찾아 실제 값과 올바른 조사로 바꿔주는 치환 엔진. 조사 판별은 유니코드 종성 유무만 보면 되는 잘 알려진 로직이라 어렵지 않다.
2. **AI 역순 일기장 + 편지 (전용 화면)** — `app/tools/encore/diary/page.tsx`(가칭) + 새 백엔드 엔드포인트 1~2개(기존 `OpenAIService` 재사용) + 이미 있는 획득 시각 데이터를 조합. 구조 자체는 소장 심문보다 단순(멀티턴 대화 상태 관리 불필요)하지만, 프롬프트 튜닝(문체 규칙 반영, 없는 기억 지어내지 않기)에 반복 작업이 들어감. 이 항목이 이번 기획에서 가장 손이 많이 가는 부분.
   - **필요한 데이터는 전부 기존 리포지토리의 읽기 전용 메서드로 확보된다(확인 완료)**: `room_clue_ownership` 리포지토리에 이미 `get_by_room(room_id)`가 있어 단서 획득 순서를 그대로 가져올 수 있고, `room_action` 리포지토리에도 이미 `get_by_room(room_id)`가 있어 단계별 AP 소모량 집계에 쓸 수 있다. 새 조회 메서드를 추가할 필요조차 없다.
   - **캐싱 필요(신규 설계 포인트)**: 매번 화면을 열 때마다 GPT를 새로 호출해 다시 생성하면 (a) 볼 때마다 다른 내용이 나와 "내 일기장"이라는 느낌이 깨지고 (b) 비용도 불필요하게 든다. 게임 완료 시점에 한 번 생성해서 결과를 저장해두고, 이후에는 저장된 걸 그대로 보여줘야 한다. 이 저장을 위한 **전용 신규 테이블**이 필요한데, 이건 도플로이드 소장 심문이 이미 쓰는 패턴과 동일하다 — 심문 기능도 `interrogation_message`/`interrogation_persona`라는 자기만의 새 테이블을 만들어 썼지, 기존 공용 테이블을 고치지 않았다.
   - **범용화 범위(결정됨)**: "다른 작품도 이런 AI 생성 엔딩 콘텐츠를 쓸 수 있게 만들자"는 제안이 있었는데, **저장 테이블의 모양만 가볍게 제너릭하게(예: `room_id` + 콘텐츠 종류/키 + 생성된 텍스트 + 생성 시각) 만들고, 프롬프트 내용·출력 구조(일기+편지 2단 구성)·화면은 이번엔 앙코르 전용으로 만들기로 확정했다.** 근거는 도플로이드 심문 기능의 실제 전례다: 그 기능도 페르소나 데이터는 `story_id` 기준으로 조회되는 제너릭한 구조지만, 실제 라우트(`/doploid/ask`)와 화면(`app/tools/doploid/interrogation`)은 작품 이름이 그대로 박힌 전용 구현이다 — 이 코드베이스가 이미 "데이터 스키마는 제너릭, 라우트·화면·프롬프트 로직은 작품별 전용"이라는 절충안을 쓰고 있다. 일기장의 경우 아직 두 번째 사례(다른 작품의 유사 요구)가 없는 상태에서 프롬프트/출력 구조까지 일반화하면 잘못된 추측으로 설계할 위험이 크다. 실제 두 번째 요구가 생기면 그때 일반화하는 게 안전하다.
3. 단계별 이미지가 뒤로 갈수록(=내부적으로는 더 오래된 기억일수록) 점점 흐릿해지는 표시 로직(완전히 안 보이게는 아니고, 상대적으로 흐릿하게). **갱신**: 몸 크기가 줄어드는 두 단계(표시 15~16년)는 이 흐림·몽환 효과를 CSS 필터가 아니라 `프롬프트.txt`에 명시된 대로 이미지 생성 프롬프트 자체에("deeply faded, dreamy and misty atmosphere" 등) 구워서 만든다 — 그 두 단계는 신규 CSS 로직이 필요 없다. 성견 구간(표시 1~14년)은 몸 크기·색상 변화가 없는 대신 4장에서 정리한 털 길이 4단계로 단계별 차이를 준다. 즉 이 항목은 CSS 흐림 로직이 아니라 대부분 콘텐츠 제작(이미지 자체 제작) 영역으로 옮겨갔다. 13장에서 다시 다룬다.
4. ~~일기장 다음에 이어지는 별도의 아웃트로(작가의 말) 화면.~~ **정정: 신규 개발 항목 아님.** 확인 결과 플랫폼에 이미 "공통 아웃트로(에필로그)" 기능이 완성돼 있다(`Step.outro` 필드 + `StepManager.tsx`의 기존 QuillEditor 입력란 + `GameEndingView.tsx`의 자동 렌더링). 마지막 단계에 아웃트로 텍스트를 써넣기만 하면 된다 — 11장 참고.
5. **단계 타이머 시스템 완성(일시정지 포함)** — 기본 골격(위 참고)은 있지만 "일시정지" 기능이 빠져 있다. 흥미롭게도 `room_step_timer`라는 테이블이 스키마에 이미 있다(`allocated_time`, `started_at`, `paused_at`, `elapsed_time`, `is_active` — room_id+step_id로 유니크). 다만 실제 코드에서는 방 삭제 시 같이 정리되는 테이블 목록에만 등장할 뿐, 이 테이블을 실제로 읽고 쓰는 리포지토리·유스케이스가 안 보인다 — 아마 시간 기반 자원 시스템이 AP로 전환되면서 쓰이지 않게 된 것으로 보인다. 이 테이블을 되살려서 제대로 된 타이머 시스템으로 완성하면 일석이조다: (a) 일시정지·재개 유스케이스와 게임 화면의 "타이머 정지" 버튼(현재 어디에도 없음, GM/방장용으로 필요)을 새로 만들고, (b) 이 테이블이 room_id+step_id로 유니크해서 **다음 단계로 넘어가도 이전 단계의 기록이 사라지지 않는다** — `current_step_started_at`과 달리 이 테이블을 쓰면 일기장(2번, 규칙 9)이 필요로 하는 "단계별 소요 시간 이력"도 별도 로그 없이 자연스럽게 확보된다.

**종합 판단**: AP 시스템, 단계 타이머 기본 골격, 질문 시스템의 주관식 지원까지 이미 있는 걸 감안하면, 정말 처음부터 새로 만드는 건 (a) 이름 치환 엔진, (b) 타이머 일시정지 기능(기존 `room_step_timer` 되살리기), (c) 일기장/편지 전용 화면과 프롬프트 튜닝 정도로 좁혀진다. 다른 방식으로 우회할 필요 없이 이대로 진행 가능한 수준이고, 처음 검토했을 때보다도 범위가 계속 줄어들고 있다.

### 우선순위

난이도가 아니라 **의존관계**를 기준으로 순서를 잡았다. 특히 5번(타이머 일시정지)은 나중에 몰아서 하면 그 사이 쌓였어야 할 소요 시간 이력이 아예 없어서 소급이 안 된다는 점이 순서를 정하는 데 가장 크게 작용했다.

1. **1순위 — 진행 시스템 기반(먼저 끝내야 뒤가 막히지 않음)**
   - **5. 단계 타이머 시스템 완성**: 가장 먼저 착수해야 한다. `room_step_timer`를 되살려 일시정지 기능과 소요 시간 이력을 확보해두지 않으면, 2번(일기장)의 규칙 9가 요구하는 시간 데이터가 나중에 하나도 없다(지나간 게임의 소요 시간은 되짚어 만들 수 없다). 기본 골격(배정 시간·자동 진행)은 이미 있으므로 실제로 만들 건 일시정지·재개 유스케이스와 GM용 정지 버튼 UI뿐이다.
   - **1. 개인화(이름 치환)**: 다른 항목과 의존관계는 없지만 범위가 작고(질문 시스템 재사용 + 치환 엔진), 먼저 끝내두면 이후 모든 텍스트 작성·테스트를 실제 이름이 들어간 화면으로 볼 수 있어 편하다. 1순위 안에서 묶어 처리.

2. **2순위 — 콘텐츠 제작 트랙(개발과 별도로, 지금부터 병행 시작)**
   - 13장의 화풍 검토·승인 → 캐릭터 시트 제작. 이건 "신규 개발"이 아니라 콘텐츠 제작이지만, 3번(흐림·색깔·크기 반영 이미지)의 절반이 여기 걸려 있다. 개발 진행과 무관하게 동시에 진행 가능한 트랙이라 지금 시작해야 나중에 병목이 안 생긴다.
   - 3번 중 **CSS 흐림 효과**는 코드로 아무 때나 붙일 수 있는 작은 작업이라 순위를 낮게 둬도 무방하다(이미지 자산이 준비되면 그때 붙이면 된다).

3. **3순위 — 핵심 기능(1순위가 준비된 뒤 본격 착수)**
   - **2. AI 역순 일기장 + 편지**: 규모가 가장 크다. 프롬프트 자체(14장 초안)는 지금도 다듬을 수 있지만, 실제 게임 데이터로 끝까지 검증하려면 1번·5번이 준비돼 있어야 한다. 전용 화면(`app/tools/encore/diary`)과 백엔드 엔드포인트 골격은 1순위 작업과 병행해서 미리 만들어둬도 된다.

4. **4순위 — 마무리(다른 항목에 안 걸리는 잔여물)**
   - **4. 아웃트로**: 신규 개발 항목이 아니게 됨(위 정정 참고) — 기존 `Step.outro` 필드에 11장 문구를 써넣기만 하면 되는 콘텐츠 작업. 다른 항목과 무관하게 아무 때나 가능.
   - **3의 나머지**: 2순위에서 캐릭터 아트가 준비되면 그때 실제 이미지로 교체.

### 기존 작품에 대한 영향

전체 항목 중 대부분(AP 시스템, 단서 획득 데이터, GPT 인프라, 전용 화면 패턴, CSS 흐림 효과)은 새 파일이나 앙코르 전용 설정값만 추가하는 방식이라 기존 작품(도플로이드, 바스타즈, 목련다방, 누룩꽃 등)에 영향이 없다. 나머지 항목들도 다시 보니 처음 생각했던 것보다 안전하다.

- **2. AI 역순 일기장 + 편지(확인 완료)**: 필요한 데이터는 `room_clue_ownership.get_by_room()`, `room_action.get_by_room()` 등 기존에 이미 있는 **읽기 전용** 메서드로 전부 확보된다 — 기존 리포지토리에 손을 댈 필요가 없다. 쓰기는 결과를 캐싱할 새 전용 테이블 하나뿐이라(도플로이드 `interrogation_message`와 같은 패턴), 다른 작품이 쓰는 어떤 테이블도 수정하지 않는다. 다섯 항목 중 4번(아웃트로) 다음으로 안전하다.
- **4. 아웃트로(정정: 확인 완료, 가장 안전 — 이유가 바뀜)**: 한때 `app/tools/encore/diary` 안에 편지 다음 화면으로 붙이는 독립 페이지로 계획했으나, 이는 틀린 판단이었다. `GameEndingView.tsx`를 직접 확인한 결과 플랫폼에 "공통 아웃트로(에필로그)" 기능이 이미 완성돼 있다 — 마지막 단계의 `Step.outro` 필드(크리에이터 화면에 이미 있는 QuillEditor 입력란)에 HTML을 써넣으면 끝이다. 11장의 아웃트로 내용은 매 플레이마다 GPT로 생성하는 게 아니라 작가가 한 번 쓰는 고정 텍스트이므로(일기·편지와 다른 점) 이 기존 필드에 그대로 들어맞는다. 새 테이블도, 새 API도, 새 화면도 전혀 필요 없다. 다섯 항목 중 유일하게 "신규 개발"이 아예 아닌 항목 — **콘텐츠만 채우면 되는 순수 작성 작업**이다.
- **5. 단계 타이머 시스템(일시정지)**: 처음엔 이 항목이 파급 범위가 가장 클 것으로 봤는데(모든 작품이 쓰는 공용 함수를 직접 고쳐야 한다고 가정했음), 실제로는 `room_step_timer`가 **현재 아무 코드에서도 읽거나 쓰지 않는 휴면 테이블**이라 오히려 안전하다. 이 테이블을 새로 wiring하는 건 기존에 아무도 안 쓰던 걸 새로 쓰기 시작하는 것이라, 다른 작품의 기존 동작을 바꿀 위험이 없다. 다만 GM용 "타이머 정지" 버튼처럼 게임 화면에 새로 노출되는 UI는, 배정 시간(`estimated_duration`)이 설정된 다른 작품에도 함께 보이게 될 수 있으니 이 부분만 확인이 필요하다(의도한 것이라면 오히려 다른 작품에도 유용한 개선이 될 수 있다).
- **1. 개인화(이름 치환)**: 서버가 단계/단서 HTML을 만들어 내려주는 공용 지점에 치환 로직을 넣어야 하는데, 이걸 모든 작품에 무조건 적용하면 다른 작품 텍스트에 우연히 `{변수명}` 패턴이 있을 때 의도치 않게 치환될 위험이 있다. **`variable_key`가 실제로 설정된 질문이 있는 작품에서만 치환이 실행되도록** 범위를 한정하면 된다 — 이건 데이터 존재 여부로 자연스럽게 게이팅되므로 별도 플래그 없이도 안전하다. 또한 질문·엔딩 규칙·답변이 전부 `story_id` 기준으로 조회되도록 이미 짜여 있어(`CalculateEndingUseCase` 확인함), 앙코르가 추가하는 질문 자체가 다른 작품 데이터에 섞일 일도 없다.

세 항목 모두 "기존 작품에 반드시 영향을 준다"는 뜻은 아니다. 오히려 하나씩 코드로 확인할수록 처음 우려했던 것보다 안전한 구현 경로가 있다는 게 계속 확인되고 있다(4번은 아예 격리, 1·5번은 데이터/설정으로 자연스럽게 게이팅).

## 13. 콘텐츠 제작 관점에서의 의견

- **재정정**: 실제 사진은 최종 결과물에 전혀 쓰이지 않는다. 사용자가 명확히 확정한 파이프라인은 "실제 사진은 어디까지나 레퍼런스"다 — 캐릭터(요크셔테리어 아리)의 생김새, 그리고 각 단서 이미지의 구도(예: "안아주기" 단서라면 실제로 안아줬던 사진의 구도)를 참고해서 그리되, 결과물은 전부 하나의 통일된 만화풍 일러스트로 새로 그린다. 즉 "캐릭터는 일러스트, 단서는 실사"라고 나눴던 직전 판단은 틀렸다 — 캐릭터든 단서든 예외 없이 전부 일러스트다.
- **화풍: 단일 기법(동화책 수채화풍)으로 확정.** 원래는 후보 4종(동화책 수채화풍, 선굵은 웹툰풍, 파스텔 플랫 벡터풍, 색연필 손그림풍) 중 세 화풍을 단계에 따라 전환하는 3단계 전환안을 검토했었다(선굵은 웹툰풍은 제외). 하지만 사용자가 직접 세 화풍을 테스트해본 뒤, 화풍은 **동화책 수채화풍 하나로 통일**하기로 확정했다. 대신 4장에서 정리한 대로 "몸 크기 + 털 색깔"(표시 15~16년) 장치와 "털 길이 4단계"(성견 구간 전체) 장치로 단계별 시각적 리듬을 준다 — 화풍 자체를 바꾸는 대신, 하나의 화풍 안에서 캐릭터 스타일링을 바꾸는 쪽으로 방향이 정리된 것이다.
- **다만 절대 지킬 조건은 그대로 유지된다**: "화풍이 상황마다 바뀌면 안 된다"는 원래 규칙의 진짜 의도는 "같은 캐릭터가 다른 존재처럼 보이면 안 된다"는 것이다. 화풍이 하나로 고정되면서 이 리스크 자체가 크게 줄었지만, 몸 크기·털 색깔·털 길이가 바뀌는 와중에도 **캐릭터의 정체성(비례, 얼굴·귀 생김새 같은 "이 개가 아리다"를 알아보게 하는 요소)은 절대 흔들리면 안 된다**는 원칙은 동일하게 적용된다.
- **실제 프롬프트는 `texts/프롬프트.txt`가 최종본이다.** 기본 프롬프트(성견 기준) + 나이·몸 크기 변형(2/3 크기·1/2 크기, 색상과 몽환적 분위기 문구 포함) + 털 길이 변형(4단계) 구조로 정리돼 있다. 화풍 3종을 비교했던 1차 테스트는 이 최종본으로 대체됐으므로, 실제 제작에는 항상 `프롬프트.txt`를 참고한다.
- **작품 대표 이미지(마켓플레이스 카드 썸네일) 구도 확정**: "돌아보는 구도"(걸어가다 뒤돌아보는 포즈)로 확정. 성견 기준 캐릭터 그대로 쓰고 새끼 시절 색/크기는 반전 신호라 표지에는 쓰지 않는다. 실제 프롬프트는 `texts/프롬프트.txt` 6장 참고.

- 다만 16단계 × 단계별 단서/AP 텍스트를 다 채우면 최소 60~100개 안팎의 짧은 텍스트를 써야 하는 분량이다. 감정적으로 소모가 큰 작업일 수 있으니, 전체를 한 번에 다 쓰려 하기보다 먼저 3~4개 단계(예: 마지막 해, 중년기, 성견 초기, 입양 첫해)만 파일럿으로 써보고 톤과 곡선이 의도대로 읽히는지 확인한 뒤 나머지를 채우는 방식을 제안한다.
- 배포 범위(비공개로 혼자/가족만 볼지, 플랫폼에 정식 공개할지)에 따라 신경 써야 할 게 달라진다. 정식 공개라면 연령 등급이나 장르 필터(현재 마켓플레이스에 "머더 미스터리" 외의 필터가 있는지)를 플랫폼 쪽에서 별도로 확인해야 한다.

## 14. 부록: 일기장·편지 생성 프롬프트 초안

10장의 GPT 호출에 쓸 시스템 프롬프트 초안이다. 실제 생성 결과를 여러 번 뽑아보며 다듬어야 하는 초안 단계이며, 특히 "AI 말투로 들리면 안 된다"는 요구를 추상적으로("자연스럽게 써라") 지시하지 않고 구체적인 나쁜 예/좋은 예를 프롬프트 안에 직접 넣어뒀다. 이래야 모델이 실제로 따라온다.

### 시스템 프롬프트

```
당신은 강아지입니다. 이름은 "{강아지이름}"입니다. 아래에서 두 가지 글을 씁니다.
- 일기: 그 나이였을 때, 그때그때 실제로 썼을 법한 일기입니다. 딱 그 순간까지 겪고 느낀 것만 압니다.
- 편지: 지금, 강아지별에서 예전 주인에게 쓰는 마지막 편지입니다. 삶 전체를 다 보낸 뒤에 씁니다.
사람이나 AI가 아니라 개의 눈으로 세상을 본 대로만 씁니다.

반드시 지킬 것:

1. 절대 AI가 쓴 것처럼 들리면 안 됩니다.
   - 정중한 안내 문구, "첫째/둘째" 같은 목록 구조를 쓰지 마세요.
   - "~인 것 같아요", "~라고 생각합니다", "~일지도 모릅니다" 같은 조심스러운 표현을 쓰지 마세요. 확신을 갖고 짧고 담백하게 씁니다.
   - 대시(—)를 쓰지 마세요. 말이 끊기거나 여운을 남기고 싶으면 말줄임표(...)를 쓰세요.
   - 어려운 단어나 복문(여러 절이 얽힌 긴 문장), "~했는지 지금도 기억난다"처럼 어른이 회상하는 듯한 문어체 구성을 쓰지 마세요. 문장은 짧고 하나의 생각만 담습니다.
   - 나쁜 예(AI스러움): "그 시절 저는 아직 너무 어렸기 때문에 많은 것을 기억하지 못하지만, 주인님과 함께한 소중한 시간들은 제 마음 깊은 곳에 남아있습니다."
   - 나쁜 예(너무 어른스러움): "이 시절의 기억은 희미하지만, 주인의 손길만큼은 온기로 남아 있다."
   - 좋은 예: "오늘은 별일 없었다. 그냥 주인 손이 따뜻했다."

1-1. **말투(문체)는 일기와 편지가 다릅니다.**
   - **일기 본문**: 반말. 유치원생이나 초등학교 저학년이 쓴 일기처럼, 짧고 쉬운 문장만 씁니다. "-다"로 끝나는 짧은 문장을 이어 붙이는 방식이 기본입니다(예: "오늘은 공을 물어왔다. 주인이 웃었다. 좋았다."). 어려운 접속사(그러므로, 따라서 등)나 관형절이 긴 문장은 쓰지 않습니다.
   - **편지(규칙 8)**: 존댓말. 주인에게 직접 보내는 글이라 "-요"/"-습니다"체로 씁니다. 존댓말로 바뀌어도 어휘 수준은 그대로 쉽고 짧게 유지합니다 — 존댓말을 쓴다고 갑자기 어른스럽고 유식한 문장이 되면 안 됩니다.

1-2. **일기는 그 순간에 쓰는 글입니다.** 나중에 무슨 일이 생길지 전혀 모르는 상태로 씁니다. 나이 든 시기의 일기에 이별을 예감하는 듯한 문장, 어린 시절 일기에 나중에 벌어질 일을 암시하는 문장(복선) 모두 쓰면 안 됩니다. 그 순간 겪은 일과 느낀 감정만 씁니다. 삶 전체를 돌아보는 시점은 오직 편지(규칙 8)뿐입니다.

2. 플레이어는 항상 "주인"이라고 부르세요. 이름이나 "당신", "너"로 부르지 마세요.

3. 개는 냄새, 소리, 온기, 거리처럼 몸으로 느낀 것 위주로 기억합니다. 날짜나 계절 같은 사람의 개념 대신 "주인이 두꺼운 옷을 입던 날", "발밑이 시렸던 날"처럼 감각으로 표현하세요.

4. "멍멍", "왈왈" 같은 의성어나 애교스러운 말투는 쓰지 마세요. 웃길 의도가 없어도 이런 표현은 진지한 순간을 가볍게 만듭니다.

5. 아래 [기억 목록]에 없는 "사건"은 절대 지어내지 마세요(예: 목록에 없는 산책, 목록에 없는 장소, 목록에 없는 사람과의 만남). 다만 그 사건에 대해 개가 느꼈을 감정과 반응은 자유롭게 표현하세요(예: 반가웠다, 무서웠다, 안심됐다, 서운했다). 사실 목록을 그대로 나열하면 일기가 아니라 보고서가 됩니다. 감정을 입히되 없는 사건을 새로 만들지는 마세요.
   - 예시: 기억이 "공을 던지자 {dog_name}는(은) 쏜살같이 뛰어가 물어왔다. 내려놓으라고 하기도 전에 다시 던져달라며 발밑에 놓았다"(7장의 1인칭 주인 관찰 기록 형태)라면 → "공을 물어다 줬다. 주인이 엄청 좋아했다. 그게 좋아서 자꾸자꾸 물어다 주고 싶었다"처럼 감정을 붙이되, "그날 공원에서 다른 강아지도 만났다" 같은 목록에 없는 사건은 만들지 마세요.
6. 어떤 시기에 항목이 적거나 없다면 그 시기는 짧게 쓰세요. 억지로 채우지 마세요. 이 여백 자체가 의미가 있습니다. **단 "그때 일이 잘 기억 안 난다"처럼 오랜 세월이 지나 회고하는 듯한 표현은 쓰지 마세요.** 일기는 그날이나 그 무렵에 쓰는 글이라, 방금 겪은 일을 두고 기억이 흐릿하다고 말하는 건 어색합니다. 대신 "오늘은 별일 없었다"처럼 그날 자체가 조용했다는 식으로 쓰세요. 기억이 흐릿하다는 인상은 텍스트가 아니라 이미지(5장의 흐림 효과)가 주는 몫입니다.

7. [기억 목록]은 오래된 기억부터 최근 기억 순서로 주어집니다. 이 순서 그대로, 시기 구분은 소제목이나 번호 없이 자연스러운 문단 전환으로 씁니다.

8. 일기 본문을 다 쓴 뒤, 반드시 한 줄을 띄우고 "===편지===" 라고 쓴 뒤, 강아지별에서 주인에게 보내는 짧은 편지를 이어서 씁니다. 이 편지가 이 글 전체의 마지막입니다. **이 편지는 규칙 1-1에 따라 존댓말로 씁니다** — 일기 본문(반말)과 말투가 바뀌는 유일한 지점입니다. 이별의 순간과 지금 이 편지를 쓰는 마음을 담되, 원망이나 슬픔보다는 함께한 시간에 대한 고마움이 중심이 되게 하세요. 이 편지에도 규칙 5(감정은 자유롭게, 사건은 목록 안에서만)가 똑같이 적용됩니다.

9. [기억 목록]의 각 항목에는 그 시기에 주인이 얼마나 시간을 썼는지(예: "5분 중 5분", "5분 중 1분"), 마음을 얼마나 표현했는지(예: "AP 7 중 5 사용", "AP 7 중 0 사용" — 예산은 항상 7이고, 그 시기 단서 개수만큼만 실제로 쓸 수 있습니다)가 함께 주어질 수 있습니다. 이 정보로 그 시기 분위기를 짐작해서 감정에 자연스럽게 녹여내되, **절대로 개가 주인을 원망하거나 탓하는 말투로 쓰면 안 됩니다.** 시간을 적게 썼거나 마음을 적게 표현한 시기라도, 서운함이 아니라 순수한 기대와 믿음으로 표현하세요. 개는 주인이 왜 그랬는지 이유를 따지지 않고, 그저 곧 다시 놀아줄 거라고 믿습니다. 이 정보를 직접 언급(예: "5분을 다 안 썼다", "AP를 안 썼다")하지 말고, 그 결과로 느꼈을 감정만 녹여내세요.
   - 나쁜 예(원망): "그때 주인은 나한테 관심 없었다. 금방 가버렸다."
   - 나쁜 예(수치 언급): "이날은 5분 중 1분만 있었다."
   - 좋은 예: "이날은 되게 짧았다. 그래도 괜찮았다. 주인이 바빴나 보다. 다음엔 더 오래 있어 줄 거다."
   - 반대로 시간과 마음을 충분히 쓴 시기는 그만큼 편안하고 충만한 기억으로 표현하세요.

10. [기억 목록]의 각 항목에는 그 시기 몸 크기(예: "성견", "성견의 2/3 정도로 작음", "성견의 절반 정도로 아주 작음")가 함께 주어질 수 있습니다. 이 정보도 직접 언급하지 말고(예: "몸이 2/3 크기였다" 금지), 그 크기에서 자연스럽게 느꼈을 몸의 감각으로 표현하세요. 몸이 작았던 시기는 계단이나 문턱이 유난히 높게 느껴졌거나, 걸음이 서툴렀거나, 주인 품에 가볍게 안겼을 수 있습니다.
   - 좋은 예: "그때는 다리가 짧아서 문턱도 잘 못 넘었다. 주인이 번쩍 안아서 넘겨줬다."
```

### 수치 기반 감정 예시 모음 (참고용)

시스템 프롬프트 안의 예시는 2개 정도로 압축해뒀다(너무 많은 예시를 프롬프트에 다 넣으면 토큰만 늘고, 오히려 모델이 예시 문장 패턴을 그대로 베끼려는 경향이 생길 수 있다). 대신 실제 튜닝(여러 번 생성해보며 결과를 다듬는 작업) 때 참고할 수 있도록, 시간/AP 조합과 삶의 시기별로 톤이 어떻게 달라져야 하는지 더 넓게 정리해둔다. "시간·마음이 많으면 행복, 적으면 아쉬움"으로 단순 이분화하지 않는 게 핵심이다.

- **시간 가득 + 마음 가득 (완전한 몰입, 성견기)**: "공을 자꾸자꾸 물어다 줬다. 주인이 계속 던져줬다. 숨이 찼는데도 계속 뛰었다. 진짜 재밌었다."
- **시간 가득 + 마음 적음 (조용한 동행, 노령기 — 결핍이 아니라 다른 형태의 충만함)**: "멀리는 못 걸었다. 그냥 마당에 같이 앉아 있었다. 주인 손이 내 등에 있었다. 그거면 됐다."
- **시간 적음 + 마음 가득 (짧지만 강렬, 바쁜 날)**: "주인이 오래 있지는 못했다. 그래도 오자마자 나를 번쩍 안아줬다. 짧았는데 좋았다."
- **시간 적음 + 마음 적음 (가장 절제된 희망, 원망 없이 — 규칙 9의 기본 예시와 다른 시기)**: "이날은 얼굴만 보고 지나갔다. 괜찮았다. 주인이 피곤해 보였다. 다음엔 놀아줄 거다."
- **노령기, 주인이 AP를 최대한 다 썼는데 몸이 못 따라준 경우 (감정과 실제 능력의 괴리 — 6장의 단서 수 곡선 설정과 직결)**: "주인이 자꾸 나를 일으키려고 했다. 예전처럼 뛰어보라고. 근데 다리가 말을 안 들었다. 그래도 좋았다. 애쓰는 손이 좋았다."
- **어린 시절, 함께할 기회가 원래 적을 수밖에 없는 시기 (소홀함이 아니라 서로 알아가는 풋풋함 — 6장에서 정한 "성견이 안 된 시기라 단서 자체가 적다"는 설정과 연결)**: "그때는 아직 낯설었다. 주인이 불러도 자꾸 딴 데를 봤다. 근데 그 목소리가 좋았다. 그래서 자꾸 따라다녔다."

### 사용자 메시지(입력) 구조 예시

```
[강아지 이름]: 아리

[기억 목록] (오래된 것부터)
1살: (기억 거의 없음) / 머문 시간: 5분 중 1분 / 마음: AP 7 중 0 사용 / 몸: 성견의 절반 정도로 아주 작음
2살: 공을 던지자 {dog_name}는(은) 쏜살같이 뛰어가 물어왔다. / 머문 시간: 5분 중 5분 / 마음: AP 7 중 3 사용 / 몸: 성견의 2/3 정도로 작음
3살: 산책 중 다른 개를 보고 짖었다가 {dog_name}는(은) 금세 꼬리를 흔들었다. / 머문 시간: 5분 중 4분 / 마음: AP 7 중 4 사용 / 몸: 성견
...
15살: 계단 앞에서 {dog_name}는(은) 멈춰 섰다. 안아서 올려줬다. / 머문 시간: 5분 중 5분 / 마음: AP 7 중 2 사용 / 몸: 성견
16살: 산책을 나섰는데 {dog_name}는(은) 얼마 못 가 안아달라고 했다. / 머문 시간: 5분 중 2분 / 마음: AP 7 중 1 사용 / 몸: 성견
```

- 실제 구현에서는 "몇 살" 대신 5장에서 정한 "실제 내부 시점(나이)"을 그대로 넣으면 되고, 플레이어가 조사하지 않은 항목은 목록에서 아예 빼거나 "(비어 있음)"으로 명시해서 규칙 5가 정확히 작동하게 해야 한다.
- 각 항목의 원문은 7장 규칙대로 건조하게 쓰인 단서 텍스트를 그대로 넣으면 된다. 감정을 입히는 건 이 프롬프트(GPT)의 역할이지, 단서 텍스트 자체의 역할이 아니다.
- **머문 시간 / 마음(AP) 필드**: 규칙 9와 짝을 이루는 입력값. 데이터 출처가 서로 다르다.
  - AP 소모량은 이미 단계별로 분리 추적된다(`room_action.used_in_step_id`로 각 액션이 어느 단계에서 쓰였는지 남고, `apInfo`가 현재 단계의 `apSpent`와 게임 전체 누적 `totalApSpent`를 따로 갖고 있음). 엔딩 시점에 단계별로 다시 집계만 하면 되므로 신규 개발이 필요 없다.
  - 머문 시간은 상황이 다르다. `room.current_step_started_at`이 "지금 단계가 언제 시작됐는지"는 담고 있지만 현재값이라 다음 단계로 넘어가면 덮어써진다. `progress_step_use_case.py`(약 416번째 줄, 이 필드를 새로 쓰는 지점) 직전에 방금 끝난 단계의 소요 시간을 계산해 별도로 남기는 작업이 필요하다. 규모는 작지만 진짜 신규 항목이다.
- **몸(크기) 필드**: 규칙 10과 짝을 이루는 입력값. 4장에서 정한 대로 내부 나이 1살은 성견의 절반, 2살은 2/3, 3살 이상은 성견으로 고정이다. 이 값은 플레이어 행동과 무관하게 나이만으로 정해지는 값이라(머문 시간·AP처럼 방마다 달라지는 데이터가 아님), 별도의 로그 저장 없이 나이 → 크기 매핑표 하나만 코드에 두면 된다. 앞의 두 필드보다 구현이 훨씬 단순하다.
- **HTML 제거 필요**: 단서 내용은 HTML로 저장되고 게임 화면에는 그대로 렌더링되는 구조라서(`dangerouslySetInnerHTML`), GPT에 넣기 전에 태그를 제거한 순수 텍스트로 바꿔야 한다.
  - 프론트엔드에는 이미 `murdex-web/lib/utils/format.ts:74`에 `stripHtml` 함수가 있다(태그 제거 + `&nbsp;`/`&lt;`/`&gt;`/`&amp;`/`&quot;`/`&#39;` 등 흔한 엔티티 수동 디코딩).
  - 다만 두 가지 문제가 있다. (1) 이 함수도 `<p>`/`<br>` 등 블록 태그를 줄바꿈으로 바꾸지 않고 통째로 지우기만 해서, 문단이 여러 개면 다 붙어버린다 — GPT 입력용으로 쓰기엔 부족한 건 마찬가지다. (2) 이건 프론트엔드(TypeScript) 함수인데, GPT 호출은 API 키를 다루는 백엔드(`murdex-api`, Python)에서 일어나야 한다(소장 심문도 같은 이유로 백엔드에 있음). 그래서 이 함수를 그대로 재사용할 수는 없고, 같은 로직을 파이썬으로 옮겨야 한다.
  - 권장 방식: 새 라이브러리(beautifulsoup4 등)를 추가하기보다, 이 프론트 함수와 같은 접근(정규식 태그 제거 + 엔티티 디코딩)을 파이썬으로 옮기되, 태그를 지우기 전에 `</p>`, `<br>`, `<li>` 같은 블록/줄바꿈 태그만 먼저 `\n`으로 치환해 문단 구분을 살리고, 엔티티 디코딩은 수동 목록 대신 파이썬 표준 라이브러리 `html.unescape()`를 쓰면 더 안전하다(목록에 없는 엔티티까지 다 처리됨). 기존 코드 스타일과 결이 비슷해서 새 의존성 없이 끝낼 수 있다.
  - 이 변환은 GPT 입력용으로만 쓰고, 게임 화면에 보여주는 단서 자체는 기존 HTML 그대로 유지한다.

### 튜닝 시 확인할 것

- 생성 결과에 em-dash, "~것 같아요" 류 표현이 섞여 나오는지 반복 검수.
- 기억이 적은 시기를 실제로 짧게/흐릿하게 처리하는지, 아니면 부풀려 채우는지 확인 — 5장의 "빈 페이지=후회" 장치가 살아있는지의 시험대다.
- "주인" 호칭이 일관되게 유지되는지.
- 편지 구분자(`===편지===`)가 매번 정확히 나오는지(파싱 안정성에 중요).
- **일기 본문이 실제로 유치원생~초등 저학년 수준으로 쉽고 짧은지**, 관록 있는 어른이 회상하는 듯한 문어체(긴 복문, "~했는지 지금도 기억난다" 류 구성)로 새지 않는지 반복 검수.
- **편지가 정확히 존댓말로 전환되는지**(일기 본문은 반말 유지), 존댓말로 바뀌면서 어휘까지 갑자기 어른스러워지지 않는지 확인.

### 일기 예시 (참고용)

일기 본문(규칙 1-1, 반말·유치원생~초등 저학년 수준)이 실제로 어떤 글이 되어야 하는지 감을 잡기 위한 예시다. 편지 예시와 마찬가지로 특정 [기억 목록]에서 뽑아낸 결과가 아니라, 규칙 1~10을 전부 반영해서 직접 써본 것이다. 오래된 기억(입양 초기)부터 최근 기억(마지막 나날) 순서로, 시기 구분 없이 문단만 자연스럽게 넘어가도록 썼다. **각 문단은 규칙 1-2에 따라 그 나이였을 때 그때그때 썼다는 전제로 쓴 것이지, 강아지별에서 삶 전체를 돌아보며 쓴 게 아니다** — 그 시점에서 앞일을 전혀 모르는 목소리를 유지해야 한다.

```
처음엔 다 낯설었다. 주인이 불러도 자꾸 딴 데를 봤다. 근데 그 목소리가 좋았다. 그래서 자꾸 따라다녔다.

문턱 하나도 잘 못 넘었다. 다리가 짧아서 그랬다. 주인이 번쩍 안아서 넘겨줬다. 그게 좋았다.

공을 처음 물어다 줬다. 주인이 엄청 좋아했다. 그게 좋아서 자꾸자꾸 물어다 주고 싶었다.

산책 갈 때마다 신났다. 냄새가 진짜 많았다. 주인은 내가 다 맡을 때까지 기다려줬다.

어느 날은 주인이 오래 못 있었다. 그래도 괜찮았다. 얼굴 보는 것만으로 좋았다. 다음엔 더 놀아줄 거라고 생각했다.

나이가 드니까 멀리 걷기가 힘들었다. 그냥 마당에 같이 앉아 있었다. 주인 손이 내 등에 있었다. 그거면 됐다.

산책이 짧아졌다. 밥을 남기는 날도 있었다. 그래도 주인 손은 늘 따뜻했다.
```

- 짚어볼 지점: 첫 문단(어린 시절, 함께할 기회가 원래 적은 시기)과 두 번째 문단(몸 크기, 규칙 10)은 앞쪽에, 마지막 문단(가장 단서가 적은 시기)은 뒤쪽에 뒀다. 실제 시간 순서로는 이게 각각 입양 초기와 마지막 나날에 해당한다.
- **단서 최소 개수와 플레이어 조사량은 다르다.** 5장에서 정한 대로 가장 단서가 적은 단계도 설계상 2~3개는 있으므로, 마지막 문단은 그 2~3개를 플레이어가 다 조사했다는 전제로 3개의 짧은 문장(산책, 밥, 손의 온기)으로 채웠다. 이게 "가장 단서가 적은 단계"의 기본형이다.
- 반면 규칙 6의 "빈 페이지" 장치는 **플레이어가 그 2~3개마저 거의 조사하지 않고 넘어갔을 때**를 위한 것이다. 이 경우는 이 문단이 훨씬 더 줄어든다: "오늘은 별일 없었다. 그냥 주인 손이 따뜻했다." 정도로. 즉 문단 길이는 "설계된 단서 수"가 아니라 "그 방에서 플레이어가 실제로 조사한 개수"를 그대로 반영해야 한다.
- **"기억이 안 난다"는 표현은 금지(규칙 6 참고)**: 일기는 그날 근처에 쓰는 글이라, 방금 겪은 일을 두고 "기억이 흐릿하다"고 말하면 회고록처럼 들려서 장르가 어긋난다. 짧은 문단이어도 "오늘은 조용했다/별일 없었다"처럼 그날 자체가 조용했다는 쪽으로 써야지, 화자가 기억을 더듬는 듯한 문장은 쓰면 안 된다. 기억이 흐릿하다는 인상은 텍스트가 아니라 5장의 이미지 흐림 효과가 담당하는 몫이다.
- 마지막 문단이 다른 문단보다 짧은 채로 끝나는 것 자체는 정상이다(단서 개수 자체가 원래 제일 적은 구간이므로). 다만 실제로 조사한 것보다 억지로 부풀려 채우면 규칙 6이 무너진다. 이 여백 뒤에 바로 존댓말 편지(아래)가 이어지면서 말투가 전환되는 구조다.

### 편지 예시 (참고용)

규칙 8이 요구하는 톤이 실제로 어떤 글이 되어야 하는지 감을 잡기 위한 예시다. 특정 [기억 목록]에서 뽑아낸 결과가 아니라, 규칙 1~10을 전부 반영해서 직접 써본 것이다. 실제 생성 결과와 비교할 기준점으로 쓰면 된다.

```
===편지===

주인에게.

저 지금 강아지별에 있어요. 여기 되게 따뜻하고 넓어요. 아픈 데도 없어요. 처음엔 좀 낯설었는데 이제 괜찮아요.

주인 손 냄새 아직도 기억나요. 처음 저를 안아줬을 때부터 마지막에 등 쓰다듬어줬을 때까지 다 기억해요. 바빠서 짧게 있었던 날도 있었고, 산책 짧게 한 날도 있었지만 저는 괜찮았어요. 주인은 항상 다시 왔으니까요. 그거면 충분했어요.

가끔 제가 더 오래 못 있어줘서 미안해요. 그래도 저는 좋았어요. 주인이랑 같이 있어서 좋았어요.

이제 여기서 기다릴게요. 천천히 오셔도 돼요. 준비되면 그때 다시 만나요. 저는 여기서 잘 지내고 있을 테니까 걱정 안 하셔도 돼요.

고마웠어요, 정말로.

아리 올림
```

- 짚어볼 지점: "가끔 제가 더 오래 못 있어줘서 미안해요"는 개가 주인을 탓하는 문장이 아니라 개 스스로가 느끼는 아쉬움이다. 규칙 9의 "개는 주인을 원망하지 않는다"는 원칙과 배치되지 않는다 — 원망의 방향이 반대다.
- 일기 본문(반말)과 이 편지(존댓말)의 어휘 수준은 같다. 존댓말로 바뀐다고 "함께한 소중한 나날이었습니다" 같은 어른스러운 문장으로 격상되면 안 된다 — "-요"만 붙었을 뿐, 여전히 짧고 쉬운 문장이어야 한다.
- 사인은 [강아지 이름] + "올림"으로 맺는다("아리 올림"). 존댓말 편지이므로 반말체였던 "씀" 대신 "올림"을 쓴다. 실제 생성 시 이 부분도 GPT가 자동으로 이름을 채우게 되므로, 사용자가 입력한 이름이 자연스럽게 붙는지 확인이 필요하다.

## 15. 실행 로드맵

지금까지 정리한 내용을 종합해 전체 진행 순서를 잡는다. 12장의 "우선순위"는 신규 개발 항목에만 한정된 순서였고, 여기서는 콘텐츠 집필·화풍 확정·개발·검증까지 프로젝트 전체를 놓고 순서를 잡는다.

1. **1단계 — 파일럿 콘텐츠 + 화풍 확정 (개발 착수 전, 지금 바로 시작 가능)**
   - 13장에서 제안한 대로 16단계 전부를 쓰기 전에 3~4개 단계(마지막 해, 중년기, 성견 초기, 입양 첫해)만 먼저 써서 톤과 단서/AP 곡선이 의도대로 읽히는지 확인한다.
   - 이 파일럿 텍스트로 14장의 GPT 프롬프트를 실제로 돌려보며 튜닝한다. 실제 콘텐츠 없이는 프롬프트 튜닝이 추상적으로만 진행될 수밖에 없었는데, 이제 실제로 검증할 수 있다.
   - 병행해서 14장 부록의 이미지 생성 프롬프트로 뽑은 화풍 3종 결과를 비교해 하나로 좁히고(또는 절충), 캐릭터 시트를 확정한다.
   - 이 단계는 전부 코드 작업이 필요 없어 바로 시작 가능하다.

2. **2단계 — 전체 콘텐츠 완성**
   - 1단계에서 톤이 확인되면 나머지 12개 단계 텍스트를 채운다. 요약 수준 개요는 `texts/16단계_전체_개요.txt`에 미리 정리해뒀다(단계별 분위기·단서 수·소재 아이디어·똘이 카메오 배치까지).
   - 확정된 화풍·캐릭터로 단서별 장면 이미지를 제작한다(실제 사진을 구도 레퍼런스로, 13장 참고).
   - 11장 아웃트로(작가의 말) 문구, 룸 로비 BGM을 이때 확정한다.

3. **3단계 — 개발 착수 (12장 우선순위 그대로)**
   - 1순위: 단계 타이머 시스템(`room_step_timer` 되살리기 + 일시정지) + 개인화(`Question.variable_key` + 치환 엔진).
   - 3순위: 일기장·편지 전용 화면 — 2단계에서 나온 실제 콘텐츠로 프롬프트를 최종 튜닝하면서 붙인다.
   - 4순위: 이미지 반영. (아웃트로는 개발 항목이 아니므로 여기서 제외 — 2단계에서 이미 기존 `Step.outro` 필드에 채워 넣고 끝남.)

4. **4단계 — 통합 테스트**
   - 처음부터 끝까지 직접 플레이하며 반전이 실제로 잘 전달되는지, 5장의 5분 조기 스킵 후회 장치가 체감되는지, 일기장 생성 결과의 톤이 규칙대로 나오는지 확인한다.
   - 가격·연령 등급 등 기본정보.txt에 제안값으로만 남겨둔 항목을 이때 확정한다.

**지금 당장 할 일을 하나만 고르면**: 화풍 테스트 결과 확인과 파일럿 3~4단계 집필을 병행하는 것이다. 둘 다 개발 착수 전에 끝나야 하고, 서로 막는 관계도 아니다.
